Exactly the 08-07 half-pixel failure mode. Now implemented exactly in new `apply_lsf()`, verified against a brute-force FFT convolution to **2e-15** of the peak.

Checked before dropping it rather than assumed: the concern was that a skewed line might bias the centroid against the finite ±1500 km/s measurement window, but at the observed 320 km/s width that window is **4.7σ** and the recovered median is exact to **0.01 km/s at α up to 4**, at both Δv=0 and Δv=+100. ## 2026-08-07 (fourth pass — a real bug in cell 8, plus the binning kernel death)
- **⚠ CELL 8'S FLUX-CONSERVATION CHECK HAD A UNITS BUG, AND IT WAS MANUFACTURING THE EXACT FAILURE IT EXISTS TO CATCH.** It multiplied the summed template by the wavelength step in **Ångström**. `SourceModel.line_profile` is normalized to unit integral in **velocity**, so the pixel width has to be in km/s: `dv_pix = c*dlam/lam0`. At z = 2.4 that is **c/lam0 = 72.5×**. The cell reported `0.0004` for a template whose true recovered fraction is **0.029** — read literally, "the normalization is off by ~70×", which is precisely the 2026-07-22-style bug this check was built to detect. The generator was fine; the check was wrong.
- **The check now compares against a prediction instead of printing a number to squint at.** Fibers do not tile the sky, so the recoverable fraction is fixed by geometry: (fibers inside the cut × fiber area / cut-disk area) × (fraction of L inside the cut radius). At 4444 fibers inside 245" that predicts **0.0246**; the corrected measurement gives **0.029**. Agreement to ~18%, which is the right tolerance — fibers live in IFUs and are not uniform over the disk, so this is a sanity bound. It still catches a stray 2π (6.28) or 1/(π·0.75²) (0.57) cleanly, which is what it is for.
- **⚠ `bin_template_radially` restarted the kernel. It was building a full float64 duplicate of every template.** The old version accumulated `pools[r]` = fancy-indexed **copies** of each exposure's fibers, cast to float64 on entry (`np.asarray(tmpl, dtype=float)`). Summed over bins that is a complete float64 copy of the entire template set — at 132 exposures × 4444 fibers × 1036 pixels, **4.9 GB** — on top of the 2.4 GB of float32 templates already live, and then `np.vstack` copied the largest bin again. Over 10 GB peak, and the outermost bin holds ~65% of the fibers all by itself.
- **Rewritten to mirror what `extract_fibers` already does for the real data** (`extract.py` §3, "gather + combine ONE BIN AT A TIME"): assign bins once into an `int16` index array, then one bin at a time with an exactly-sized **float32** pool, freed before the next bin, in wavelength blocks. `method="mean"` builds no pool at all — it streams a running sum and count. Measured at 40 exposures: **peak extra RAM 9 MB (mean) / 20 MB (median, biweight)**, down from ~10 GB, and mean is 0.1 s. Verified identical to the old implementation: `mean` bit-for-bit, `median` agreeing to 6e-8 above 1e-4 of the bin peak (the residual is float32 wing underflow) and **7e-6 km/s on the centroid**.
- **Notebook now bins on the static 1-D fiber distance, matching production.** `extract.py` builds `bin_idx_all` from `dist_arcsec_all[e]` — per fiber, no DAR. The cell was computing `nanmedian(hypot(2-D DAR-shifted), axis=1)`, which sorts 4444 rows of 1036 pixels to reproduce the same number to within the sub-arcsec DAR excursion: **0.197 s per exposure, now 0.0001 s**.

## 2026-08-07 (third pass — the ring kernel, and a diagnostic so this stops recurring)
- **⚠ ~23 s per exposure remaining, and it was neither the PSF table nor the fibers: it was the ring kernel, rebuilt every exposure for no reason.** `_shell_to_fiber_kernel` is `n_r × n_shell × n_phi` interpolations — **399 radii × 1005 shells × 180 angles ≈ 72 million**, per call. It depends only on the radius grid, the shell grid and the seeing; **nothing about the fibers enters it**. But `r_uniq` was being built from *this exposure's* `nanmin`/`nanmax` fiber radius, which wiggles by a fraction of an arcsec between exposures, so every exposure got a marginally different grid and paid the full 72 million again.
- **Fix: quantize the grid bounds so they are bit-identical across exposures, then cache the kernel.** `r_lo` pinned to 0, `r_hi` rounded up to the next 5", `grid_max` rounded up to the shell step. New `_KERNEL_CACHE` keyed on (response, seeing, those bounds) — no fiber quantity in the key, which is the point. Measured over 24 exposures: **first 1.6 s, every subsequent one 0.06 s**; total 3.0 s where it was ~35 s, with **one** kernel built instead of 24. Combined with `SEEING_MODE="field"` this is what makes the loop finish. Accuracy against exact bounds with 15× denser grids and a 0.1" shell step: per-fiber 2.6e-3, **binned profile 5.6e-4, Δv 0.006 km/s**; `check_level0` passes for P, H, H(α=2).
- **New `injection.time_template_build()` — run it on one exposure before committing to the loop.** Three timing failures in this cell in one day, each with a different cause, each diagnosed only by interrupting after 30+ minutes and reading a traceback. The question that separates all three cases is one measurement: **cold vs warm**. `cold >> warm` means the cost is shared work paid once (fine); `cold ≈ warm` means it is genuinely per-fiber (fewer fibers or fewer pixels are the only levers); and warm *not* dropping when it should means a cache key is being broken by something varying per exposure. It also prints `n_r × n_shell × n_phi`, which is the number that actually drives the cost — if that comes back far above ~7e7, a grid bound has blown up and that is the bug, not the machine. Called from cell 7. Also `clear_injection_caches()`, needed when monkeypatching a response function (the cache keys use `id(response)`).

## 2026-08-07 (second pass — the *time* problem, after the memory one)
- **⚠ Same cell, different bottleneck: ~10 minutes PER EXPOSURE, all of it inside `moffat_psf_integration`.** With the memory blowups fixed the cell ran, but slowly, and the traceback landed on `extract.py:1651` — the innermost line of the production Moffat loop. Cause: the V(separation) table was `geomspace(1e-3, d_max, 3000)`. **A geometric grid spends its knots equally per decade**, and separations run 1e-3" to ~500", so **two thirds of the 3000 knots landed below 6.25"** — precisely the region `fiber_response_hybrid` serves from the *production* path, where each knot means a fresh 281×281 Cartesian grid and boolean aperture mask inside a Python loop. ~2000 expensive knots × 3 bracket seeing values = **~6000 grid builds per exposure**, and none of it cached because the seeing changes every exposure (2.20, 2.30, 2.12, …). The knots outside 6.25" — the other third, and the ones actually spanning the halo — were analytic and effectively free. The grid was spending all its effort where the source barely is.
- **Fix: budget the knots by cost, not by decade.** New `_separation_table` splits at `PSF_GRID_VALID_ARCSEC` (the same 6.25" where hybrid hands over from production to analytic, so "expensive knot" and "near knot" are the same set by construction): **100 knots inside, 500 outside**. Inside 6.25" V is a smooth PSF core that 100 knots resolve to ~1e-4 — below what the far side is accurate to anyway.

Net effect is a radial ramp that suppresses the center and pushes the model's peak outward; nearly harmless at a narrow PSF (R barely mixes radii, so the two errors largely cancel within a bin) and catastrophic once a realistically wide PSF makes R mix flux across radii. **This is the identical defect that was found and fixed in the UV path back on 2026-07-15/17 (`bin_average_psf_uv_exp`, whose own docstring already names the symptom: "runaway chi^2 when a real (large) PSF FWHM was passed") — the fix was simply never back-ported to the Lyα models.** All four Lyα entry points (`bin_average_psf`, `bin_average_psf_expcore`, `bin_average_no_psf`, `bin_average_no_psf_expcore`) now use `(R @ [I(r)*2*pi*r*dr]) / annulus_area`; `_annulus_areas`/`_fine_ring_flux_2d`/`_bin_integrate_2d` promoted into Part 1 and reused by the UV models (`_fine_ring_flux_uv_2d` kept as an alias). The two UV *naive* functions were fixed at the same time — they were still on the width convention while their own PSF counterparts were not, so `method='naive'` and `method='psf'` UV fits were not measuring the same quantity. `ring_convolution_matrix` (R) is **unchanged** and still passes `validate_ring_convolution`; the old 1-D helpers are retained but marked DEPRECATED.
- **Diagnosis and verification: `01-lya_halos/code/psf_forensics.py`** (new, standalone, does not import into the pipeline). Four tests against real data + a brute-force 2-D image convolution reference: (1) corrected form agrees with brute force to <1% at both 1.3″ and 2.4″ PSF FWHM while the old form was off by **51% and 96%** respectively, error growing monotonically with PSF width; (2) deconvolvability check (`data / point-source PSF` must be non-decreasing) **passes for both PSF widths — so the 2.4″ PSF measurement was never the problem**; (3) simple fit ladder (`A·PSF` → `A·PSF+C` → `PSF ⊛ A·exp(-r/h)` → `+C`) gives a stable h under the corrected convention at both widths (15.14±1.03 kpc at 1.3″, 12.02±0.99 kpc at 2.4″, χ²/dof 1.07 and 1.42) while the old convention collapses to h→5.09 then h→0.011 at 2.4″; (4) FWHM sweep 1.0″–3.0″ gives smooth h = 15.9→10.1 kpc with χ²/dof 1.07–1.77 and **no cliff anywhere**. Post-fix regression: `bin_average_psf_expcore` matches brute force to ≤0.65% at 10.9/20.1/30.0 kpc FWHM (error no longer grows with width), and noiseless injection–recovery returns `h1`/`A1`/`A2` exactly for both the `psf` and `naive` paths.
- **Consequences to act on.** (a) Every PSF-aware Lyα fit run before today is affected — `h1`, crossover radii, zone luminosities and the subsample splits all need re-running. (b) Fitted amplitudes `A1`/`A2` are now central **surface brightnesses**; absolute pre-fix and post-fix amplitudes are not comparable (scale lengths, crossover radii and amplitude *ratios* are). (c) The r≈48 kpc residual that had been flagged as a separate unresolved anomaly appears to have been this same bug — the old model's error peaked at exactly those radii, and inner-only χ² is now 3.21 across 5 bins with no outlier. (d) The extension is detected overwhelmingly: `psf_only` gives χ²/dof 44–94, and adding the single parameter `h` drops χ² by ~173. (e) Still genuinely open: the data only mildly prefer 1.3″ over 2.4″ (Δχ²≈1 on 3 dof, not significant), but that choice moves `h` from ~15.1 to ~12.0 kpc — roughly 3× the statistical error, so **PSF width is now a systematic to quote rather than a bug to chase**. (f) See the separate quadrature entry below — the ~2.8% inner-bin discretization error first attributed to `n_per_bin` was a quadrature-rule bug, now fixed for free.
- **Radial quadrature rule fixed — 113× more accurate at the same cost, so `n_per_bin` stays at 30.** The ~2.8% innermost-bin error against exact quadrature looked like "not enough grid points," but raising `n_per_bin` only converged it as 1/n (0.81% at 100) while tripling the grid (378 → 1218 points) and therefore roughly tripling the `ring_convolution_matrix` build, which is essentially the entire runtime of a fit (the fit itself is ~0.02 s). The actual cause: `default_fine_grid` gives each observed bin its own `linspace`, so grid spacing JUMPS at every bin edge (up to 2.5× on the real 12-bin scheme), and `np.gradient` is a central difference — a point on a bin edge got a weight averaging the spacing on both sides, and `np.add.at` then assigned that single shared point's entire weight to one bin, so the lower bin silently lost its outer endpoint, exactly where its `2*pi*r` weighting is largest. Replaced with a per-bin composite trapezoid rule: new `_segment_weights` (used by `_fine_ring_flux_2d`, which now takes `r_edges`; all four PSF call sites updated) and `_bin_integrate_2d` rewritten to `np.trapezoid` over each bin's own sub-grid with both endpoints included. **Innermost-bin error 2.772% → 0.0245% at the unchanged `n_per_bin=30`** — 33× better than `n_per_bin=100` was under the old rule, at zero runtime cost. PSF path still matches brute-force 2-D convolution to ≤0.65% at 10.9/20.1/30.0 kpc FWHM (that residual is the reference's own pixelization), and noiseless injection–recovery is still exact on both the `psf` and `naive` paths.
